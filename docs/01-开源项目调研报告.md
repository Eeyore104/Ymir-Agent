# ymir-agent 开源项目调研报告

> **调研人**：许清楚（产品经理） | **调研时间**：2026-10-12 | **模式**：市场/竞品调研（GitHub 开源项目方向）
> **调研对象**：与"多 Agent 协作完成软件开发全流程（需求→设计→代码生成→评测→落地）"定位接近的开源项目
> **数据说明**：所有 Star 数、版本、活跃度均来自 2026-06 至 2026-10 的联网检索结果（GitHub 页面、GitHub API 快照第三方站、官方 README），不同来源快照时间不同，表中以"量级"呈现并在附录注明。

## 一、调研结论先行（TL;DR）

**核心问题：能不能基于现有开源项目二次开发，做出 ymir-agent？**

**答：不存在"拿来即用"的单一开源底座，但存在一条被验证可行的"组合式"路线。** 现有开源项目分处三个层次，没有任何一个同时覆盖"需求→设计→代码生成→评测→落地"全流程：

1. **多角色软件公司模拟**（MetaGPT、ChatDev）——有完整的角色/SOP 设计思想，但只做到"生成代码+文档"，无评测体系、无部署落地，且 MetaGPT 社区活跃度已明显下滑（最后提交 2026-01，最近 Release 为 2025-03 的 v0.8.2）。
2. **通用 Agent 编排框架/平台**（Dify、Coze Studio、CrewAI、LangGraph、AgentScope）——平台能力成熟（工作流画布、RAG、模型管理、可观测），但默认不内置"软件工程全流程 SOP"，需要自行定义 PM/架构师/工程师/QA 角色与流程。
3. **自主编码 Agent**（OpenHands、SWE-agent、Aider、Cline）——代码生成与沙箱执行最强，SWE-bench 评测文化成熟，但不覆盖需求/设计阶段。

### 首选推荐（按优先级）

| # | 推荐 | 角色定位 | 核心理由 |
|---|------|---------|---------|
| 1 | **Dify（langgenius/dify，~15 万 Star）** | **平台底座（fork 或深度集成）** | 全球最成熟开源 LLM 应用平台：可视化工作流、模型网关、RAG、HITL 审批、可观测、插件/MCP 生态齐全；2026-07 已发布沙箱版 Dify Agent（Linux sandbox + Skills）。私有化单租户部署**不受**其修改版 Apache-2.0 的多租户限制约束。改造点：把"软件公司 SOP"沉淀为工作流模板 + 自定义 PM/架构师/工程师/QA 节点。 |
| 2 | **OpenHands（All-Hands-AI，~7.5-8 万 Star，MIT）** | **工程执行引擎（集成/复用，不 fork）** | 开源自主编码 Agent 标杆：Docker 沙箱隔离、Agent Server REST API、K8s 多租户+RBAC、SWE-bench Verified 53%-72.8%；2026 年已演进为 Agent Canvas"多 Agent 控制平面"，通过 ACP 协议可调度 Claude Code/Codex 等任意编码 Agent。其 `software-agent-sdk` 可直接作为 ymir-agent 的"工程师角色"执行内核。 |
| 3 | **MetaGPT（geekan/MetaGPT，~7 万 Star，MIT）** | **设计思想与角色体系来源（借鉴+SOP 抽取，慎选为底座）** | 唯一原生就是"多角色 AI 软件公司"（PM/架构师/工程师/QA + SOP + 文档先行）的开源项目，与 ymir-agent 定位最契合；但社区活跃度下滑（2026-01 后基本停更，148 contributors，144 open issues），商业重心已转向 MGX。**建议借鉴其 Role/Team/Message 抽象与 SOP 机制，不作为长期演进底座。** |

### 一句话架构建议

**"Dify 做平台壳（前端+工作流+模型管理+可观测） + 自研轻量多 Agent 编排内核（借鉴 MetaGPT 角色 SOP + LangGraph 状态图） + OpenHands SDK 做代码生成/沙箱执行 + SWE-bench 式 harness 做评测"**，Java/uni-app 侧通过 Spring Boot 微服务与 MCP/A2A 协议衔接（可参考 AgentScope Java / Spring AI Alibaba、京东 JoyAgent 的 Java 栈）。

## 三、分类评估

### A 类：可直接 fork 做底座二次开发

| 项目 | 判断 | 改造点 |
|---|---|---|
| **Dify** | **首选底座**。私有化单租户部署可正常商用（其修改版 Apache-2.0 仅限制多租户 SaaS 运营与去 logo）。 | ① 将"软件公司 SOP"沉淀为工作流模板与自定义节点（PRD 生成→架构评审→任务拆解→编码→测试→部署）；② 用 v1.16 的 Dify Agent 沙箱承接工程师角色执行；③ 前端增加"团队/项目/任务看板/产物版本管理"；④ 接 MCP/A2A 对接外部编码 Agent 与 Java 侧服务。**注意**：若未来想做多租户 SaaS 必须购买商业授权。 |

## 四、与用户需求的差距分析

| # | 差距 | 说明 | 对 ymir-agent 的启示 |
|---|------|------|---------------------|
| 1 | **全流程无人覆盖** | MetaGPT 到"代码+文档"止步；OpenHands 从 issue 起、到 PR 止；Dify/Coze 是通用平台不含软件 SOP；秒哒全流程但闭源 | 全流程串联本身就是 ymir-agent 的**核心差异化价值**，须自建 SOP 编排层 |
| 2 | **评测体系缺口** | SWE-bench 只评"修 bug"；缺乏 PRD 质量、架构合理性、需求符合度、代码可运行率、部署成功率的**全链路评测** | 自建评测维度（可借鉴 SWE-agent harness + OpenHands Index 思路） |
| 3 | **私有化/企业级** | Dify 多租户需商业授权；Coze 部分能力依赖火山引擎；多数项目无 RBAC/审计/多租户 | 明确私有化单租户定位可绕过 Dify license 限制；RBAC/审计需自建 |
| 4 | **与 Java/uni-app 栈衔接** | 底座几乎全是 Python；AgentScope Java 与 JoyAgent 是少数 Java 友好选项；主流编码 Agent 对 Java/Spring Boot/RuoYi/vue 的生成质量远弱于 Python/JS | Java 侧建议独立微服务（MCP/A2A 对接）；代码生成质量需针对性评测与 prompt 工程 |
| 5 | **平台化功能缺口** | 多数项目是框架/库，缺"项目管理、任务看板、人机审批流、产物版本管理、成本看板" | 这些正是平台层要补的，可基于 Dify 壳扩展 |
| 6 | **成本与可控性** | 自主 Agent token 消耗大且不可预测；SWE-agent 的实例级预算上限是少数好实践 | 内置预算控制、模型分级路由（贵模型规划/便宜模型执行，参考 Aider Architect 模式） |
| 7 | **社区依赖风险** | MetaGPT 停更、Devika 休眠、GPT-Pilot 停更+安全事件、Roo-Code 2026-05 关停、AutoGen 官方维护模式——明星项目死亡率高 | 架构上保持"引擎可替换"（ACP/MCP 协议化解耦），勿与单一项目深度绑定 |

## 五、给主理人的行动建议：接下来该问用户的关键问题

按优先级排序，建议主理人在架构设计前与用户确认：

1. **部署定位**：私有化单租户（个人/企业内部）还是多租户 SaaS？——直接决定能否以 Dify 为底座（多租户需商业授权），以及是否需要 RBAC/租户隔离。
2. **技术栈取向**：后端跟随主流用 Python（生态最全），还是坚持 Java/Spring Boot（用户背景 + JoyAgent/AgentScope Java）？前后端用什么（Vue/uni-app？）？——决定底座选型与 Java 侧衔接方式。
3. **"落地"的定义**：落地=生成可部署的 Docker/K8s 制品？还是要直接部署到用户内网并交付？是否需要对接用户已有 RuoYi/uni-app 项目做代码生成？
4. **MVP 范围**：第一版做哪几个角色（建议 PM+工程师+QA 三角）、跑通哪段流程（建议 需求→PRD→架构→代码→单元测试）？评测与部署是否第一期就要？
5. **人机协同深度**：哪些节点强制人工审批（PRD 确认/设计评审/代码合并/部署发布）？审批在平台内做还是对接 IM（飞书/钉钉）？
6. **模型策略**：接哪些 LLM（国内 DeepSeek/Qwen/GLM/Kimi？海外 Claude/GPT？）？是否必须支持本地模型（Ollama/vLLM）私有推理？月度 token 预算量级？
7. **沙箱方案**：本地 Docker 隔离是否可接受？是否需要 K8s 多租户沙箱（参考 OpenHands v1.6+）？代码在用户内网执行还是平台侧？
8. **架构偏好**：接受"平台壳(Dify) + 自研编排 + 引擎复用(OpenHands SDK)"的组合架构，还是倾向尽量单一底座 fork（如 JoyAgent-JDGenie 全 Java）？
9. **用户规模与商业模式**：自用/小团队（<50 人）还是企业多团队？未来是否可能商业化（影响 license 策略，如 AGPL/修改版 Apache 的选择）？
10. **评测优先级**：是否接受"先跑通流程、第二期再建自动化评测"的节奏，还是评测体系必须与流程同步建设？
