## 1. 环境要求

| 组件 | 版本 / 说明 | 是否必需 |
|---|---|---|
| Python | 3.12（建议用 [uv](https://docs.astral.sh/uv/) 管理虚拟环境与依赖） | 必需 |
| uv | 最新版；安装后 `uv` 通常在 `~/.local/bin` | 必需 |
| Node.js | ≥ 18（前端控制台；建议 LTS） | 可选（只用 API/CLI 可跳过） |
| Docker Desktop | 用于沙箱执行不可信代码；不可用时自动降级 LocalSandbox | 可选（推荐） |
| DeepSeek API Key | 真实模型调用；沙箱镜像预装依赖，装依赖场景才需联网 | 必需（真实跑角色） |

> **0 费用开发模式**：单测与 e2e 全部 mock LLM（见第 7 节），无需密钥即可跑 `uv run pytest`。

### 1.1 Windows：uv / Python 环境

```bash
# 安装 uv（Windows PowerShell 或 Git Bash）
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
# 或 pip install uv

# Git Bash 里 uv 可能装在 ~/.local/bin，需加入 PATH
export PATH="$HOME/.local/bin:$PATH"
```

### 1.2 Docker 安装指引（沙箱用）

沙箱默认在 Docker 内执行代码（断网 + 资源限额）。按你的 Windows 版本选择：

**A. Windows 11（推荐）**

1. 开启 WSL2：管理员 PowerShell 执行 `wsl --install`，重启；
2. 安装 Docker Desktop for Windows（勾选 *Use WSL 2 based engine*）；
3. 验证：`docker version` 能打印 Client/Server 版本；
4. 拉取沙箱基础镜像：`docker pull python:3.12-slim`
   （或构建定制镜像：`docker build -f docker/sandbox.Dockerfile -t ymir-sandbox .`）。

**B. Windows 10（Build 19041 及以上，即 2004/20H2 及更新）**

1. 前置：**必须开启 WSL2**（Docker Desktop 的 Hyper-V 后端已停止维护）。
   管理员 PowerShell：`wsl --install`；如提示不支持，先
   `dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart`
   与 `dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart`，重启；
2. 安装 WSL2 内核更新包（微软官方 msi），`wsl --set-default-version 2`；
3. 安装 Docker Desktop → Settings 勾选 *Use the WSL 2 based engine*；
4. `docker run --rm hello-world` 验证。

**C. 无 Docker / WSL2 不可用**

无需额外操作：`sandbox_backend=auto`（默认）会在探测失败时**降级 LocalSandbox**
（subprocess + 资源限额；隔离性弱化，仅限本机单人场景），功能可跑通、评测照常。
如需强制降级：`.env` 设 `YMIR_SANDBOX_BACKEND=local`。

## 2. 配置 .env

```bash
# 仓库根目录
cp .env.example .env        # Windows: copy .env.example .env
```

编辑 `.env`，至少填入模型密钥（**密钥只放 .env，永不入库**）：

```dotenv
DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxx
# 可选：调整默认值与沙箱行为
YMIR_SANDBOX_BACKEND=auto        # auto | docker | local
YMIR_SANDBOX_NETWORK=none        # none | restricted | open
```

- `config/models.yaml`：模型档位与路由（planner=deepseek-reasoner / executor=deepseek-chat）、
  失败降级链、预算红线（单 run 50 万 token / UTC 日 ¥50）；
- `config/pipelines/software-dev.yaml`：四阶段流水线（prd → architecture → coding → evaluation）；
- `config/roles/*.yaml`：四角色定义。**改流程 / 换模型 / 加角色全部改配置，不改代码**。

## 3. 初始化与一键启动

```bash
# 1) 安装后端依赖
uv sync

# 2) 初始化数据库（SQLite，位于 data/ymir.db）
uv run alembic upgrade head

# 3) 安装前端依赖（首次）
cd web && npm install && cd ..

# 4) 一键启动（后端 8000 + 前端 5173；Ctrl+C 一并退出）
bash scripts/dev.sh
```

启动后：

- 后端 API / 接口文档：<http://127.0.0.1:8000/docs>
- 前端控制台：<http://127.0.0.1:5173>

> 也可分别启动：后端 `uv run uvicorn ymir.api.app:app --port 8000 --reload`，
> 前端 `cd web && npm run dev`。

**可选 · 容器化一键启动（Docker Compose）**：本机无需安装 Python / Node 亦可整栈拉起：

```bash
docker compose up -d    # 后端 :8000 + 前端 :5173（首次拉镜像并装依赖，耗时较长）
docker compose down     # 停止并移除容器（保留数据卷）；`down -v` 则连数据卷一并清除
```

数据（SQLite / 产物）与容器内依赖均存于命名卷，宿主目录零污染；容器内默认 Local 沙箱
（`YMIR_SANDBOX_BACKEND=local`），如需真实 Docker 沙箱见 `docker-compose.yml` 文件内注释。

## 4. 四角色全流程操作（浏览器）

打开控制台 <http://127.0.0.1:5173>，依次：

1. **项目看板（/）**：`新建项目` → 填名称/描述；
2. 点击项目行的 `发起运行`，输入原始需求（如「实现一个待办事项 REST API」），
   选择 HITL 模式：
   - `关键节点审批`（默认）：三关人审（PRD 确认 / 设计评审 / 代码合并前）；
   - `批量自动通过`：关卡自动通过（保留审计轨迹），适合全自动跑分；
   - `全步骤调试`：每个阶段都暂停等待审批；
3. 进入 **运行详情（/runs/:id）**：
   - `流水线阶段` 看板实时推进（SSE 事件驱动，断线自动重连 + seq 重放；
     服务端彻底关闭时前端**主动重建**并显式携带 `after_seq` 续传，事件按 seq 去重，不丢不重）；
   - `人工审批` 卡片出现时：`通过` 继续，或填反馈 `驳回`（角色带反馈修订重跑，
     产物版本递增 v1 → v2…）；
   - `实时事件` / `角色消息` 面板可追溯全过程；
   - 右上可 `暂停 / 恢复 / 重试当前阶段 / 取消`；
4. 运行完成后，到 **产物库（/artifacts）** 查看 PRD / 设计 / 代码 / 评测报告，
   支持按文件树浏览、版本 **diff**，右上角 **导出 zip** 可整库下载（含 manifest.json）；
5. **审批中心（/approvals）**：跨运行的待审批聚合列表与决策；列表项已内联 run 摘要与
   历史反馈链，**点击「待审产物」按钮可查看该产物内容**（文件清单 + Markdown 渲染）；
6. **评测报告（/evaluation）**：查看四维评分与证据链；工具栏 / 空态可 **发起四维评测**
   （选项目 / 目标产物 / 套件 / 版本），详情加载失败可内联重试；标 **降级** 的维度表示
   评估器异常或沙箱不可用，分数仅供参考（见第 5 节）；
7. **设置（/settings）**：后端健康探测、模型网关脱敏视图、**路由候选链与预算红线**、
   **沙箱会话状态**（`Local 降级` 标识）与 token / 成本用量。

### 4.1 单跑演示（命令行，真实编排链路）

```bash
# 单跑 PM：需求 → PRD v1（产物 / 消息 / 事件 / 用量全量落库）
uv run python scripts/run_single_role.py --requirement "做一个命令行待办清单工具"

# 跑到指定角色（自动含上游链；engineer 阶段含沙箱冒烟）
uv run python scripts/run_single_role.py --requirement "..." --role engineer

# 演练：不调模型，打印阶段链与模型档位
uv run python scripts/run_single_role.py --requirement "x" --role qa --dry-run
```

## 5. 评测使用（四维报告 + 批量跑分）

评测套件定义于 `evals/suites/*.yaml`（默认 `default`）：四维权重
（需求 30% / 可运行 30% / 规范 20% / 架构 20%）+ 双门槛
（`总分 ≥ 75` 且 `可运行率 ≥ 60`）。每个分数都附**证据链**（文件 / 命令输出 / judge 理由片段）。

### 5.1 Web 端

- 打开 **评测报告（/evaluation）**：列出全局（或某项目，带 `?project_id=`）报告，
  点击查看单份报告的四维分数、证据链与通过判定；
- **发起四维评测**：工具栏 `发起四维评测` 或空态 `立即评测` → 选项目 / 目标产物 /
  套件 / 版本（留空取最新）→ 提交后自动刷新列表并提示总分与判定；
- 维度标 **降级**（`degraded`）表示该维因评估器异常 / 沙箱不可用未走完正常判定，
  分数仅供参考，勿直接当作产物劣质。

### 5.2 命令行批量跑分

```bash
# 对项目 code 产物 v1、v2 批量跑分（纯确定性口径，0 费用）
uv run python scripts/run_eval.py --project-name demo --versions v1,v2 --no-judge

# 单版本 + 真实 judge（需 .env 密钥；产生评测成本）
uv run python scripts/run_eval.py --project-id <id> --suite default --save

# 机读 JSON 输出（供 CI / 回归对比）
uv run python scripts/run_eval.py --project-id <id> --versions latest --json
```

输出：每份四维报告 + **性价比榜单**（`total_score` vs `cost_cny` 表格）。

> **回归基线**：套件任务的 `requirement` 固定；任何提示词 / 角色 / 流水线变更后重跑，
> 分数变化即回归信号。评测报告作为一等产物入库（`type=report`），可对两次报告做版本 diff。

### 5.3 评测 API（供集成）

| 端点 | 说明 |
|---|---|
| `GET /api/v1/evaluations` | 全局评测报告列表 |
| `GET /api/v1/projects/{id}/evaluations` | 项目评测报告列表 |
| `POST /api/v1/projects/{id}/evaluations` | 对项目某产物发起评测（返回完整报告） |
| `GET /api/v1/evaluations/{id}` | 报告详情（按报告产物 ID 读四维分数 + 证据链） |

> **v1.1 双报告类型**：列表与详情同时支持 `evaluation_report`（QA 叙事报告）与
> `eval_verdict`（流水线内 harness 确定性裁决，唯一裁决源）。列表项新增 `kind` 字段
> 区分两者；详情两种都能打开，返回同一 `EvaluationReport` 结构（含追溯四字段
> `run_id / artifact_version / repair_round / verdict_source`）。

## 6. 导出与备份

### 6.1 导出项目 zip

- **Web**：产物库页右上角 **导出 zip** 按钮；或直接访问
  `GET /api/v1/projects/{id}/export` 下载 zip；
- zip 内含各产物最新版本内容 + `manifest.json`（含版本历史元数据），可解压还原项目全貌。

### 6.2 data/ 备份（SQLite + 产物）

运行时数据全部在 `data/`（已在 `.gitignore`，不入库）。建议定期快照：

```bash
# 方式一：整目录快照（最简，含 SQLite + artifacts）
cp -r data "backup/data-$(date +%Y%m%d-%H%M%S)"

# 方式二：data/ 建独立 git 仓库做版本化备份
cd data && git init && git add -A && git commit -m "snapshot $(date +%F)" && cd ..

# SQLite 一致性热备（服务运行中也安全）
sqlite3 data/ymir.db ".backup 'backup/ymir-$(date +%Y%m%d).db'"
```

### 6.3 清理演示 / 遗留数据

# 预览将删除的项目

## 8. 常见问题

| 现象 | 处理 |
|---|---|
| `uv: command not found`（Git Bash） | `export PATH="$HOME/.local/bin:$PATH"` |
| 健康页模型网关显示 `no-key` | `.env` 未配 `DEEPSEEK_API_KEY`，或未重启后端 |
| 沙箱降级 LocalSandbox | Docker 未启动 / Win10 未开 WSL2；见 1.2 |
| 前端 `npm run build` 报类型错 | 先 `cd web && npm install` 补齐依赖 |
| 运行卡在某关 | 属正常：`关键节点审批` 模式需在审批中心 / 运行详情决策 |
| 预算超限 `budget.exceeded` | 调 `config/models.yaml` 的预算红线后 `恢复` run |
| 接口返回 `500` | 未预期的服务端异常（内部错误码；见 8.1 速查表） |

### 8.1 接口错误码速查

| 业务码 | 含义 | 常见场景 |
|---|---|---|
| `1001` | 参数错误 | 产物名不存在 / 非法 decision |
| `1002` | 资源不存在 | run / 审批 / 产物 / 报告不存在 |
| `1003` | 状态冲突 | 重复审批决策（并发下仅一方成功） |
| `1004` | 预算超限 | 单 run token 或日成本击穿红线 |
| `1005` | 沙箱错误 | 沙箱不可用 / 读写失败 |
| `1006` | 模型调用失败 | 输出校验重试耗尽 / 上游异常 |
| `500` | 内部错误 | 未预期的服务端异常（对齐 docs/02 §6.3） |

> run 失败时错误码同时落在 `run.error_code` 字段与 `run.failed` 事件载荷，前端在运行详情
> 的错误行以标签展示（如 `1006 · 模型调用失败`）。

## 9. v1.1 新增能力（自愈回环 / 批量基准 / 人工介入）

v1.1 在 v1.0 线性流水线上加了一条**声明式回边**：`coding → evaluation` 裁决未达标时，
自动带「失败检查 + 上一版产物 + 修复指令」重跑 coding（**轮次与预算双重守门**），
并通过 SSE 事件把每一轮修复暴露到前端「修复时间线」。本章覆盖这条链路新增的三个操作面。

### 9.1 基准批量跑分（`scripts/run_benchmark.py`）

对 12 条基准任务（`evals/suites/benchmark-12.yaml`）逐任务起真实 run、跑分、落基线表。
**与 `run_eval.py` 的区别**：`run_eval` 评「已有产物」，`run_benchmark` 从需求**生成**产物再评。

```bash
# 1) 校准：先跑 3 个（部分执行，报告标注 limit=3 + partial=true）
uv run python scripts/run_benchmark.py --suite benchmark-12 --limit 3 --no-judge

# 2) 续跑：读状态文件，跳过 status=done 的任务（skipped 会重试）
uv run python scripts/run_benchmark.py --suite benchmark-12 --resume --batch-id 20261019-a

# 3) 全量 + 批次实测成本硬上限（命中即停止，剩余任务 skipped{budget}，零模型调用）
uv run python scripts/run_benchmark.py --suite benchmark-12 --budget-cny 20 --batch-id 20261019-a

# 4) 只重算基线表（不发起任何 run，用于改渲染 / 补字段后重出）
uv run python scripts/run_benchmark.py --suite benchmark-12 --batch-id 20261019-a --report-only
```

| 参数 | 语义 | 默认 |
|---|---|---|
| `--suite` | 套件 ID，须 `binding_mode: per_task` | `benchmark-12` |
| `--batch-id` | 批次标识（状态文件键 + 项目名前缀） | 按 UTC 日期生成 |
| `--limit N` | 本次最多发起 N 个任务；报告标注「部分执行」 | 全量 |
| `--resume` | 读状态文件，跳过 `status=done` | 关 |
| `--budget-cny X` | 批次**实测成本**硬上限（`SUM(model_calls.cost_cny)`，含 judge） | 无上限 |
| `--no-judge` | 纯确定性口径（judge 成本 0，用于零费用演练 / 复现） | 关 |
| `--sandbox-image` | 沙箱镜像 tag | `YMIR_SANDBOX_IMAGE` 或 `ymir-sandbox:latest` |
| `--concurrency` | **固定 1**（单 run 串行，v1.x 再放开） | 1 |
| `--report-only` | 只重算基线表，不发起 run | 关 |
| `--json` | 以 JSON 打印基线表（机读） | 关 |

**启动预检（强制，失败即退出、不发起任何 run）**

| 检查 | 判定 | 失败动作 |
|---|---|---|
| 套件绑定模式 | `binding_mode == per_task` | `InvalidParamError`(1001) |
| 镜像存在 | `docker image inspect <image>` 成功 | **exit 2** |
| 镜像内 pytest 可用 | `python -m pytest --version` exit 0 | **exit 2** |
| 镜像内 ruff 可用 | `ruff --version` exit 0 | **exit 2** |
| 网络策略 | 固定 `network=none`（镜像已预置依赖，评测期不联网） | `InvalidParamError`(1001) |

预检失败的 stderr 会给出**唯一**修复命令：

```bash
docker build -f docker/sandbox.Dockerfile -t ymir-sandbox:latest .
```

> 刻意**不会**回退到 `python:3.12-slim`（无 pytest / ruff）——那种镜像会静默跑出一张
> 全红基线，比没有基线更有害。预检通过后镜像 tag 与 `pytest/ruff` 版本号写入状态文件
> `meta.image` / `meta.image_probe`，作为**本次基线的执行环境指纹**。

**产物**

| 文件 | 说明 |
|---|---|
| `data/benchmark/state-<suite>-<batch>.json` | 断点续跑状态（**原子写**：tmp + `os.replace`，中断不产生半截 JSON） |
| `data/benchmark/baseline-<batch>.md` | 人读基线表 |
| `data/benchmark/baseline-<batch>.json` | 机读（metadata + rows + summary） |

基线表表头必含：跑分时间 / 批次 / `limit`+`partial` / 模型路由 / judge 模型与温度 /
沙箱类型 + 镜像 tag + probe / network / 套件与流水线版本 / 成本口径（实测）/ 
`executed`+`skipped` / 首轮与最终通过率 / `score_source` 分布。
行内 `score_source` 区分 `pipeline`（流水线内裁决）与 `fallback`（脚本事后补评）；
**首轮通过率只统计 `pipeline` 行**，`fallback` 行单列披露，两类不混算。

**RK6：两种沙箱不得合并出表**。`docker` 与 `local` 两批口径不同（后者无 pytest / ruff，
`runnability` 会走静态降级），混在一张表里会误导读者 —— 混表直接抛 `InvalidParamError`(1001)；
基线表强制标注沙箱类型，**要对比就先各自出表**。

### 9.2 人工介入（`scripts/run_action.py`）

修复耗尽（`rounds_exhausted`）或预算中断（`budget_exceeded`）后，由人决策下一步：

```bash
# 接受「最优未达标版本」：failed -> completed（取 total 最高那一轮，并列取 round 最大）
uv run python scripts/run_action.py <run_id> --action accept-best --by alice

# 追加 1 轮修复：先过预算预检，通过后 extra_rounds+1 并回到 coding 重跑
uv run python scripts/run_action.py <run_id> --action extend-repair

# 终止（保留现场：产物版本 / 评测报告 / 失败分类都不删）
uv run python scripts/run_action.py <run_id> --action cancel

# v1.0 四动作同样可用
uv run python scripts/run_action.py <run_id> --action pause|resume|retry-stage
```

`--db` 指定 SQLite 文件（缺省 `settings.db_path`，通常 `data/ymir.db`）；`--by` 是审计人标识
（`accept-best` 会写进 `context.repair.accepted.accepted_by`）。非法动作名由 argparse 拦下，
**退出码 2**；业务错误（run 不存在 / 状态冲突）**退出码 1**。

| 动作 | 前置 | 效果 |
|---|---|---|
| `accept-best` | run 为 `failed` 且 `context.repair.history` 非空 | `failed → completed`；写 `context.repair.accepted{version,total,runnability,accepted_by,at}` + `stop_reason="accepted"`；发 `repair.accepted` + `run.completed{accepted_unqualified:true}` |
| `extend-repair` | run 为 `failed` 且 `history` 非空 | **预算预检**（未过则 `BudgetExceededError` 1004，run 保持 failed）→ 作废 coding 与下游已完成执行 → `extra_rounds += 1`、`current_stage_id = repair.stage` → `running` 并发 `repair.started{manual:true}` |
| `cancel` | 任意非终态 | `→ failed`（`error="cancelled by user"`），版本 / 报告 / 分类全部保留，可 `retry-stage` |
| `pause` / `resume` | `running` / `paused` | 挂起推进 / 继续（预算提额后用于恢复） |
| `retry-stage` | `failed` | 从当前阶段 `attempt+1` 重跑 |

> **CLI 是「离线控制面」**：动作落库并置 `running`，**推进任务需由 API 服务启动时的
> recovery 接管**（`run_action.py` 自身进程退出即结束，不承担执行面）。
> 服务在运行时，请改用 HTTP：`POST /api/v1/runs/{id}/actions`（body `{"action": "..."}`）。

### 9.3 断点恢复语义（`--resume` / 引擎 recovery）

服务启动时 `recover_runs()` 扫描未终态 run 并决定恢复方式：

| 中断时状态 | 恢复行为 |
|---|---|
| `running` | 从 `current_stage_id` **重新执行**该阶段（`attempt+1`）；残留 `running` 的阶段执行记录被标记 `failed`（现场保留） |
| `waiting_approval` | 原地恢复等待（审批记录不丢，决策后继续推进） |
| `paused` | **不自动推进**：需人工 `resume`（通常是预算提额后） |
| `pending` | 从未开始，按新建 run 处理 |

批量跑分的 `--resume` 是**另一层**语义：读 `data/benchmark/state-*.json`，
只跳过 `status=done` 的任务（`skipped` 会重试），与引擎的 run 级恢复互不影响。

> 组合用法：`run_action.py extend-repair` 把 run 置 `running` 后退出 → **重启 API 服务**
> （或对服务进程执行 recovery）即由引擎接管重跑；CLI 本身不会推进。

### 9.4 前端新增（修复时间线 + 报告追溯）

- **运行详情**：新增「修复时间线」面板（阶段看板下方）。每轮一块：`第 N 轮` + 状态
  （修复中 / 已通过 / 已耗尽）+ 分数 + 耗时；展开可见**触发原因**（`evaluation.failed` 的
  分数、失败分类、失败检查前 3 条）、成本、产物版本跳转；耗尽轮显示可执行动作提示
  （`accept-best` / `extend-repair`）。**无回边的 run 不出现该面板**。
- **评测报告**：头部新增四只读徽标 —— `run <id>`、`code v<版本>`、`第 N 轮修复`、
  `裁决来源 harness / llm_qa`（`harness` 绿、`llm_qa` 灰）；列表项 `kind="eval_verdict"`
  额外打标。QA 叙事分数不进顶部（裁决口径见 `docs/07 §4.4.1`）。

### 10.1 上传基线（在现有项目上改）

把用户已有工程打包上传，成为该项目的**不可变基线产物**（`type=baseline`），后续增量生成以它为起点。

**入口**：`POST /projects/{project_id}/baselines`

**请求方式（两种，都不是 multipart）**

| 通道 | `Content-Type` | 说明 |
|---|---|---|
| 前端 / 二进制 | `application/zip` + **原始字节** | 浏览器侧 `axios.post(url, file, { headers })`，**不要用 `FormData`** |
| 脚本 / 测试 | `application/json` | body 形如 `{"files": {"<相对路径>": "<文件内容>"}}` |

> **为什么不用 `multipart/form-data`**：FastAPI 的 `UploadFile` / `Form` 会隐式依赖 `python-multipart`，
> 本项目刻意**不引入**该依赖（`pyproject.toml` / `uv.lock` 里没有它），上传能力因此改为上面两条无表单通道。

**限制与拒绝行为**

| 项 | 规则 | 超限结果 |
|---|---|---|
| 文件数 | **≤ 300** | 1001 |
| 总体积 | **≤ 5MB** | 1001 |
| zip slip 三类 | `../x`、绝对路径（`/etc/x`）、Windows 盘符（`C:/win`） | 1001，**磁盘无残留**（所有校验先于落盘） |
| 重复/前缀冲突 | 归一化后同路径、或 `a` 与 `a/b` 同时存在 | 1001 |

**示例（curl）**

```bash
curl -X POST "http://localhost:8000/api/v1/projects/$PROJECT_ID/baselines" \
  -H "Content-Type: application/zip" \
  --data-binary @my-project.zip
```

**示例（Python）**

```python
import httpx, pathlib

data = pathlib.Path("my-project.zip").read_bytes()
r = httpx.post(
    f"http://localhost:8000/api/v1/projects/{project_id}/baselines",
    content=data,                              # 原始字节，不是 files=
    headers={"Content-Type": "application/zip"},
    timeout=60,
)
print(r.json())   # {"code":0,"data":{"artifact_id":"...","version":1,"content_hash":"...","file_count":42}}
```

**说明**

- 上传成功后成为 `name=baseline`、`type=baseline` 的产物，版本**不可变**，重复上传产生 v2、v3…
- 基线**不参与** `GET /projects/{id}/export` 的默认导出（避免把"用户原工程"当成果重复打包）；
  需要带基线的导出请用 `?mode=merged`。
- 响应里的 `content_hash` **必定非空**（这是快照指纹）；而历史产物版本的 `content_hash` 可能为空，前端空值显示 `—`。

### 10.2 增量模式（`from_scratch` vs `patch`）

发起 run 时选定基线，该 run 的模式即为「**增量**」（`run.context.baseline` 落引用；不选基线则是 `from_scratch` 从零生成）。

**模型产出什么**

- 只输出**新增 / 修改**的完整文件；要删除的路径写进 `deleted` 清单（**不要**写空文件占位）；
- 与基线**逐字节相同**的文件会被自动丢弃（不再报错）——模型即使"重出整棵树"，也会自动退化为增量；
- 产物里带 `patch_manifest.json`（机器簿记，≤2KB）：`base_content_hash` / `changed_paths` / `counts`
  （added / modified / deleted / noop_dropped）/ `skeleton_added` / `reserved_conflicts` / `conflicts`。

**评测口径（重要）**

- **评的是「基线 ⊕ 补丁」的整棵合并树**，不是只评增量文件：只评增量会掩盖"改坏了原来能跑的东西"的回归；
- judge 语料**分级**控制成本：变更文件给全文，未变更文件**只给路径清单**；
- **基线指纹不匹配时**（`run.context` 的版本取不到、且 `base_content_hash` 在本项目里反查失败）：
  **不合并、不评测该补丁的分数**，报告标注「本次未使用基线，分数与基线内运行不可比」，并按 `unknown` 降级
  **不阻断**流水线。**不会**"偷偷拿最新基线顶上"——静默错误比报错贵。

**多轮**

- 一次 run = 一个补丁，基于一个基线版本；
- 追加需求请显式「**以合入结果为新基线**」（`POST /projects/{id}/baselines/from-merge`），
  **不**自动把多轮补丁链式叠加（链式叠加顺序敏感、无法回滚）。

### 10.3 推送到 GitHub

把产物（或「基线 ⊕ 补丁」的合并树）推送到指定仓库，**1 次推送 = 1 个 commit**（Git Data API）。

**配置**

```bash
# .env（Token 只从环境变量读，禁止写进请求体、禁止提交）
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
```

- **最小权限**：classic PAT 只需目标 repo 的 `repo` scope；**fine-grained PAT** 请授予 `Contents: Read and write`；
- 请求体**不接受** `token` 字段（带了直接 1001）；未配置 token 时应用仍能正常启动，
  推送接口返回 `failed/no_token`（**0 网络请求**），不影响生成/评测链路。

**默认落点与安全阀**

| 项 | 默认行为 |
|---|---|
| 分支 | 推到**新分支** `ymir/<artifact>-v<n>`（不动用户主分支） |
| `main` / `master` | 需显式 `allow_protected_branch=true`（该字段在 `target` 内）+ 前端二次确认，否则 1001 且**不发网络请求** |
| dry-run | 建议先 `dry_run=true`：只做过滤与清单，**不推送**，返回 `status=ok, dry_run=true` |

**密钥防护（双层）**

- **路径黑名单 12 类**：`.env`、`*.key`、`*.pem`、`*.p12`、`id_rsa*`、`.ssh/**`、`.aws/**`、`.netrc`、`.npmrc`、`.pypirc`、凭据 json、`data/ymir.db*`、`.git/**` 等；
- **内容指纹 5 类**：`AKIA…`（AWS）、`sk-…`（OpenAI 风格）、`ghp_…`（GitHub token）、`BEGIN … PRIVATE KEY`、`xox…`（Slack）；
- 命中即**剔除**并在响应的 `blocked_files` 里披露（`strict_secret_check=true` 时整体失败）；
- **白名单例外 3 个**：`.env.example` / `.env.sample` / `.env.template` 属**文档模板**，**允许推送**。

**错误码与幂等**

| 情况 | 错误码 / 结果 |
|---|---|
| 推送尝试失败（鉴权 / 权限 / 配额 / 网络 / 分支保护） | **1007**（`ExportError`，HTTP 502） |
| 产物或通道（repo / branch）**不存在** | **1002**（资源未找到，不是失败域） |
| 同 key 且远端 head 未变 | `status=skipped_identical`（不重复提交，返回原 `commit_sha`） |

- **失败时回执已落库**（审计不丢），错误响应体本身**不含回执**；事后可通过
  `GET /projects/{project_id}/exports` 查看每一条尝试（含 `error_class` / `error_message`）。

**示例（curl · 先 dry-run）**

```bash
curl -X POST "http://localhost:8000/api/v1/projects/$PROJECT_ID/exports" \
  -H "Content-Type: application/json" \
  -d '{"artifact_id":"<ARTIFACT_ID>","artifact_version":null,"tree":"merged",
       "target":{"repo":"your-name/your-repo","branch":"ymir/demo-v1","allow_protected_branch":false},
       "dry_run":true}'
```

**示例（curl · 真推）**

```bash
curl -X POST "http://localhost:8000/api/v1/projects/$PROJECT_ID/exports" \
  -H "Content-Type: application/json" \
  -d '{"artifact_id":"<ARTIFACT_ID>","artifact_version":null,"tree":"merged",
       "target":{"repo":"your-name/your-repo","branch":"ymir/demo-v1","allow_protected_branch":false},
       "dry_run":false}'
```

> 响应 200 时 `status=ok` + `commit_sha`；失败时按上表返回 1001 / 1002 / 1003 / 1007。
> 注意 `allow_protected_branch` 必须写在 `target` 内（放到顶层会被 `extra="forbid"` 拒成 1001）。

> **`artifact_version` 的缺省语义（容易踩）**：不传或传 `null` 时取该 artifact 的**最新版本**。
> 所以「推首版全量」和「推某轮增量」必须显式区分 —— 增量产物只含变更文件，**不会**重复携带
> 基线里已有的骨架文件（如 `.env.example`）。实测过：同一 artifact 先跑过增量（v2）后，
> 缺省推送推的是 v2（22 文件、无 `.env.example`）；要推首版完整文件集需显式
> `"artifact_version": 1`（27 文件、含 `.env.example`）。

### 11.2 `data-pipeline`（数据管道 / 定时任务）

- **目录规范**：必须有 `pipeline/`、`tests/`；产物路径只能落在 `pipeline/`、`tests/` 下；禁 `venv` / `.venv`；单文件 ≤600 行；Python 文件名 snake_case。
- **骨架**：`pyproject.toml`、`ruff.toml`（固定提供，不要输出）/ `pipeline/__init__.py`、`requirements.txt`（已给最小版本，需输出完整版）。
- **提示词口径**：数据读取 / 清洗 / 写出必须拆成**可单测的纯函数**（DataFrame → DataFrame），I/O 与调度放最外层；禁用 Web 框架与前端。
- **检查命令**：`python -m compileall -q pipeline`、`python -m pytest -q`、`ruff check .`、`python -c "import pipeline"`、`python -c "import pandas"`。
- **依赖白名单**：`[pytest, ruff, pandas, numpy]` —— 四个包都是镜像内**真实可 import** 的（v1.3 起），模型可直接 `import pandas`，无需联网安装。

### 11.3 `node-express`（Express + TypeScript）

- **目录规范**：必须有 `src/`、`tests/`；禁 `node_modules` / `dist`；产物路径只能落在 `src/`、`tests/` 下。
- **骨架**：`package.json`（`build: tsc -p tsconfig.json`、`test: node --test dist`，**固定提供，改动会改检查口径**）、`tsconfig.json`（`strict` + `outDir=dist`）、`.env.example`（固定提供）/ `src/index.ts`（监听入口）、`src/app.ts`（可测试的 `createApp()` 工厂）。
- **提示词口径**：必须区分「可测试的 app 工厂」与「监听端口的入口」；**禁止** `npm install` / `npm ci` / `npx -y`（沙箱断网，依赖由镜像提供）；测试用 Node 内置 `node --test`，不要引入 jest。
- **检查命令**：`node-build .`（镜像内构建脚本 / 离线依赖兜底）、`node --test dist`、`npx tsc --noEmit`。
- **依赖白名单**：`[express, typescript, @types/express, @types/node]` —— 与镜像内 `/opt/node-baseline` 一致。

### 11.4 受保护路径（增量模式专用）

**解决什么**：v1.2 真跑两次复现同一问题 —— 模型在增量模式下"顺手重写" `tests/conftest.py`，
导致基线既有测试集体失效（`DATABASE_URL` 被 `lru_cache` 吞掉 / 收集期 `ImportError`）。
加提示词约束**无效**，所以改成服务端硬约束。

**模板怎么声明**

```yaml
protected:
  paths:
    - tests/conftest.py     # 精确文件
    - tests/fixtures/       # 或以 "/" 结尾 = 目录前缀（同 layout.allowed_prefixes 约定）
  on_hit: reject            # reject（默认）| ignore
  max_change_ratio: 0.5     # 改动面告警阈值（0, 1]，默认 0.5
```

现有四套模板都声明了受保护夹具：python 三套保护 `tests/conftest.py`，`node-express` 保护 `tests/setup.ts`。

**服务端怎么处置（三段式，保证不整轮报废）**

| 段 | 行为 | 成本 |
|---|---|---|
| ① 首次合并 | 模型输出命中受保护路径 → 抛 `ProtectedPathConflict`（业务码 `1003` / HTTP `409`，`details.reason="protected_path"`） | 1 次模型调用（已花） |
| ② 定向重试 | **恰好 1 次**：把「受保护路径清单 + 请改用新文件」经反馈通道回喂模型重跑 | 第 2 次模型调用（成本累加进同一阶段） |
| ③ 兜底 | 仍撞墙 → 以 `ignore` 策略再合一次：**保留基线版本**、丢弃模型内容、manifest 记 `protected_path_forced_ignore:<n>`，阶段继续 | 0 次模型调用（纯函数） |

`on_hit: ignore` 的模板跳过 ①②，直接在第 1 段保留基线版本。

**你在审批卡片上会看到什么**

- 产物里的 `patch_manifest.json` 增加三个纯增量键（**默认值不写入**）：
  `change_ratio`（改动面小数）、`warnings`（机器短码，如 `change_ratio_exceeded:0.78` / `protected_path_ignored:1`）、
  `counts.protected_hits`。**逐字节口径**：只有「本次没有任何变更」（`changed_paths` 为空）或
  `from_scratch` 时正文才与 v1.2 完全一致；真实的增量补丁会多出一个 `change_ratio` 键 —— 这是
  "非默认值才序列化"的必然结果，不是缺陷；
- 审批卡片「待审产物」标题旁出现徽标：`改动面 78%，建议复核` / `受保护路径命中 1 处`（无数据时整块隐藏）。

**边界（如实说明）**

- 受保护路径**只在增量模式（有基线正文）生效**：从零生成时模型必须能创建 `tests/conftest.py`，否则产物缺夹具；
- 删除同样被拦：写进 `deleted` 也保留基线版本（否则可用删除绕过硬约束）；
- 改动面 **只告警不阻断**：超阈值只影响 manifest 与徽标，不改分数、不回边。

### 11.5 镜像边界（哪些检查依赖镜像、断网时各自 behavior）

镜像是**一切执行的前提**（沙箱默认 `network=none`），所以"检查能不能跑"完全取决于镜像里有什么：

| 检查 / 能力 | 依赖镜像里的什么 | 断网时 behavior |
|---|---|---|
| `python -m pytest` / `compileall` / `ruff check` | pip 预装（pytest 8.x / ruff 0.6.x） | 正常工作 |
| `python -c "import pandas"`（data-pipeline） | pip 预装 pandas / numpy | 正常工作（v1.3 起**真的能过**） |
| `python -c "from app.main import app"` | pip 预装 fastapi / uvicorn / sqlalchemy[asyncio] 等 | 正常工作 |
| `fe-build web`（fastapi-vue3 前端构建） | node 20 + npm + `/opt/fe-baseline/node_modules`（vue/vite/element-plus/vue-tsc）+ `/opt/npm-cache` | ① 项目带 `package-lock.json` ⇒ `npm ci --offline` 命中本地缓存；② 没 lock 或缺包 ⇒ **回退** `/opt/fe-baseline/node_modules`（`cp -an`，不覆盖模型文件）；③ 再跑 `npm run build` |
| `node-build .`（node-express 构建） | node 20 + npx + `/opt/node-baseline/node_modules`（express/tsc/@types） | 同上；无 `build` 脚本时 `npx --no-install tsc -p tsconfig.json` |
| `node --test dist` | node 20 内置 test runner（零依赖，**不用** jest） | 正常工作 |

**模型自己装依赖**：一律**不允许**（沙箱断网）。模型只能写进 `requirements.txt` / `package.json`；
**能 import 什么，由镜像决定** —— 这就是"依赖白名单 ⊆ 镜像清单"（校验 4）存在的原因。

> **构建/换镜像的两条纪律**：① 代码默认引用 `ymir-sandbox:latest`，`docker build` 后**必须**
> `docker tag ymir-sandbox:<tag> ymir-sandbox:latest`（只打自定义 tag 会导致真跑时 `fe-build` 不存在）；
> ② 改 `SANDBOX_IMAGE_PACKAGES` / `SANDBOX_IMAGE_NODE_PACKAGES` 必须与 Dockerfile 与两个
> `docker/*-baseline/package.json` **同一 PR**（B14）。

**降级行为（T2.4）**：若某个环境确实缺工具链（例如旧镜像没有 node），带 `requires` 的检查会被判为
`skipped`（`skipped_reason=requires_missing:<bin>`）：**不进可运行率分母、不扣分、不阻断**，
报告会写「前端构建未执行（环境缺失）」。**绝不**因为环境缺失把好代码判 fail。

`requires` 的探测方式：执行检查前先跑 `command -v <requires>`，非 0 即跳过。
命中的跳过会同时出现在两处：报告的「已跳过检查（不扣分）」行（`TaskOut.skipped_checks`）、
以及 `TaskOut.warnings` 里的「前端构建未执行（环境缺失：node/npm 不可用）」。

> **镜像内版本号是实测口径，不是契约**：pytest / ruff / pandas / numpy 的具体版本随镜像构建时的
> pip 解析结果而定（本轮实测值见 `docs/11 §8.1`）。要确认当前镜像到底装了什么，直接跑：
>
> ```bash
> docker run --rm --network none ymir-sandbox:latest sh -c \
>   'python -m pytest --version; ruff --version; python -c "import pandas, numpy; print(pandas.__version__, numpy.__version__)"; node --version; npm --version'
> ```

**手工复现离线构建**（排查"为什么模型产物构建不过"最常用的一步）：

```bash
# 把产物树放到某个空目录（假设为 ./art ）
docker run --rm -it --network none -v "$PWD/art:/workspace" ymir-sandbox:latest sh -lc '
  cd /workspace
  fe-build web    # 前端（fastapi-vue3）；node 项目用 node-build .
  echo "exit=$?"; ls -la web/dist 2>/dev/null | head'
```

脚本的两条路径都会打印在 stdout 上：`npm ci --offline 命中本地缓存` 或 `回退预置基线 node_modules`
（后者的最后 5 行 `npm ci` 日志会被带出来，用于定位"缺哪个包"）。

### 11.6 前端构建检查与分组配分（`fastapi-vue3`）

v1.3 起 `fastapi-vue3` 的 checks 分三组，`runnability` 维度改用**分组配分**（其余三套模板不变，仍是
v1.2 的"按权重归一"老口径 —— 这是分数可比性的分界线）：

| 组 | 点数 | 由什么打分 | 折算到**总分** |
|---|---|---|---|
| `backend` | 10 | 4 条 Python 检查（compileall / pytest / ruff / import app，组内权重 1/2/1/1） | 10 分 |
| `frontend_static` | 10 | 前端结构规则（目录 / `*.vue` 匹配 / 禁用依赖），**静态检查** | 10 分 |
| `frontend_build` | 10 | `fe-build web`（离线 `npm run build`，组内权重 2，**阻断项**） | 10 分 |

算式：`组内得分 = Σ权重(通过) / Σ权重(非 skipped) × 100`；`维度分 = Σ点数×组得分 / Σ点数`。
**四维权重（30/30/20/20）与双门槛（75/60）一字未改。**

三条口径（都写进代码了）：

1. **环境缺失不扣分**：整组 `skipped` ⇒ 该组**不进分母**（不是 0 分）；
2. **构建失败即阻断**：`blocking: true` 的检查失败 ⇒ `passed=False`、verdict `fail`，
   但**分数照算照披露**（报告会出现「总分 78.00 / 未通过：阻断项失败（fe-build web）」）；
3. **前端结构分只算一次**：搬到 `runnability` 后，`convention` 维度不再重复计。

### 11.7 新增模板的准入清单（贡献者 5 步）

1. 复制一套最接近的 YAML，改 `id`（必须等于文件名主干）/ `name` / `stack` / `layout`；
2. 骨架 **3–5 个**文件、总字节 ≤32KB，且**不含任何测试文件**（否则结构分会白送）；
3. `checks` 至少 1 条执行型命令，且**离线可跑**（禁 `http(s)://` / `pip install` / `npm install`）；
   依赖镜像外工具链的检查必须写 `requires: <可执行文件名>`；
4. 声明 `protected.paths`（测试基础设施）；`on_hit` 缺省 `reject`；
5. `uv run python -c "from ymir.templates import load_template; load_template('<id>')"` 过全部 **21 条**加载期校验，
   并补一条 `tests/test_templates.py` 结构用例。

### 11.8 只有增量模式会看到的东西（`patch_manifest.json` 速查）

| 键 | 何时出现 | 含义 | 谁读它 |
|---|---|---|---|
| `mode` / `changed_paths` / `counts` / `conflicts` | v1.2 起一直有 | 合并模式、变更集、计数、冲突 | 评测语料分级、审批卡片、导出 |
| `change_ratio` | **v1.3，且本次确有改动时**（>0 才写） | 改动面 = `changed_paths / 基线文件数`，两位小数 | 审批卡片徽标「改动面 78%，建议复核」 |
| `warnings` | **v1.3，且触发时才写** | 机器短码：`change_ratio_exceeded:0.78` / `protected_path_ignored:1` / `protected_path_forced_ignore:1` | 审批卡片、基线表 |
| `counts.protected_hits` | **v1.3，且 >0 时** | 被拦截的受保护路径条数 | 审批卡片徽标「受保护路径命中 N 处」 |
| `conflicts[].reason = protected_path` | v1.3 | 命中受保护路径（`ignore` 策略下记） | 人审定位 |

> **字节口径（重要，别误判为缺陷）**：v1.3 的新键**只在非默认值时序列化**。因此
> ① `from_scratch` 产物（没有 manifest）与"本次无任何改动"的补丁，正文与 v1.2 **逐字节一致**；
> ② 真实增量补丁只要改了东西就必然多出 `change_ratio` 键 —— 这是"非默认值才写"的必然结果。

## 12. v1.3 分数口径断点（**与 v1.2 基线不可横比**）

v1.3 有五处会**改变分数本身**（不是改分数公式，而是改输入或分配方式）。拿 v1.3 的分数去和 v1.2 的
基线表比高低，结论一定错。逐条说明 **变了什么 / 谁受影响 / 怎么读**：

| # | 断点 | 变了什么 | 受影响对象 | 怎么读 |
|---|---|---|---|---|
| **B1** | `fastapi-vue3` 改走**分组配分** | 可运行率维度内按 `backend 10 / frontend_static 10 / frontend_build 10` 计点（前端 20 分、后端 10 分）；其余模板仍是"按权重归一" | **只有 `fastapi-vue3`** | 同一产物在 v1.3 与 v1.2 下的 `runnability` / `total` **必然不同**，属预期；其余三套模板分数口径不变 |
| **B2** | 路径白名单修复（`allowed_files`） | `convention` 结构规则里「路径落在允许前缀内」一条，v1.2 对**每套模板都恒判失败**（`README.md` / `pyproject.toml` 等根级文件不属于任何目录前缀）；v1.3 起模板自己声明的根级文件自动放行 | **四套模板全部**（含 python-cli / 新增两套） | v1.3 的结构分**整体抬高**约 1/规则数 的比例；这是**修 bug**，不是放松标准 |
| **B3** | 前端从"只静态检查"变成"**真构建**" | `fastapi-vue3` 多了 `fe-build web`（阻断项）；前端结构规则仍保留但改由 `runnability` 计分 | `fastapi-vue3` | 前端坏掉的项目在 v1.3 会**直接 fail**（v1.2 只是扣结构分）；这是 Q4 的刻意收紧 |
| **B4** | 镜像内容变了 | 新增 node20 工具链 + 两个离线依赖池 + pandas/numpy；镜像 968 MB | 所有依赖镜像的检查 | **v1.2 没装 pandas 的镜像里 `import pandas` 必然失败**，v1.3 起能过；跨版本重跑必须在**同一镜像**下比较，否则差异来自环境不是代码 |
| **B5** | 新增两类失败分类 | `baseline_unhealthy`（排最前）/ `regression`（排 `check_failed` 前） | 基线表 `failure_class` 列 | 这两列只在 v1.3 新数据里出现；旧状态文件重渲染结果不变 |

### 12.1 三类"看起来像分数变化、其实不是"

1. **环境缺失跳过 ⇒ 分母变小 ⇒ 分数变高**：带 `requires` 的检查被跳过时**不进分母**（不是按 0 分算）。
   同一产物在"有 node"与"没 node"的镜像里跑，`runnability` 会不同 —— 报告会写「已跳过检查（不扣分）」，
   别把"没装 node"读成"前端变好了"。
2. **阻断项失败 ⇒ 未通过但分数可能很高**：报告允许出现「总分 78.00 / ❌ 未通过：阻断项失败（fe-build web）」。
   读结论看 `passed` / verdict，不要只看分数。
3. **基线不健康 ⇒ 分数不可比**：`baseline_runnability.status = unhealthy` 时，这行的分数**与健康基线不可比**
   （`comparable=false`），任务裁决按 `unknown` 处理（不回边、不阻断）。此时该看的是"基线为什么坏"。

### 12.2 怎么得到可比的对照

| 目的 | 做法 |
|---|---|
| 与 v1.2 比模型能力 | **不要比**。要么在同一版本内比（同镜像、同套件、同模板），要么用 `python-cli`（口径未变）做纵向对照 |
| 复查某次分数 | `uv run python scripts/run_single_role.py --requirement "…" --role engineer --evaluate --suite default`（与 gate / 批量**同一装配点**，容差 0） |
| 批量对照 | `uv run python scripts/run_benchmark.py --suite benchmark-12 --no-judge --batch-id <新批次>`，**新批次单独出一张表**，不覆盖历史文件 |
| 判断"是不是回归" | 看 `TaskOut.regression` / 基线表 `failure_class=regression`：基线健康但合并树失败 = 增量改坏了既有功能 |

> 口径权威：`docs/11 §7.5-4`（算式）、`docs/11 §8.2`（19 条实施偏离，含"字节级契约收紧"与"镜像超 DoD"）、
> `docs/02 §12.1 补充`（分组配分与 8 类失败分类）。本文只讲**怎么用 / 怎么读**。
