## 1. 结论

**v1.1 核心目标达成**：评测从「单次打分」升级为「基准批量跑分 + 不达标自动返工 + 耗尽后人工介入」，全链路在真实模型、真实 Docker 沙箱下跑通，并用 benchmark-12 的部分执行（3/12）产出可复现基线表。

| 目标 | 结论 | 关键证据 |
|---|---|---|
| 评测任务绑定与基准套件 | ✅ | `per_task` 绑定、`benchmark-12`（12 任务/12 场景）、未绑定零成本跳过 |
| 声明式回边与自愈 | ✅ | `repair` 块 + 9 条加载期校验；fail→定向修复→pass 全链路事件 |
| 三重守门 | ✅ | 轮次 / 单 run 预算（fail-closed）/ 批次成本上限；两种终态字段不串味 |
| 终局审批语义 | ✅ | 中间候选 defer（仅 key_node）、终局只审一次、防刷屏、驳回真重跑 |
| 人工介入 | ✅ | accept-best / extend-repair / cancel（API + CLI），落库留事件 |
| 可观测与追溯 | ✅ | 6 个事件全字段 + SSE 重放；报告含 run_id/版本/轮次/来源；前端修复时间线 |
| 真跑基线 | ✅ | 3 任务：首轮 33.3% → 最终 100%，成本 ¥0.8828，见 §4 |

## 6. 过程中发现并修复的真实缺陷

| # | 缺陷 | 发现方式 | 影响 | 修复 |
|---|---|---|---|---|
| 1 | 评测产出被修复轮覆盖（per-attempt 重名） | T3.2a 实现自检 | 修复轮产物互相覆盖，历史不可追溯 | per-attempt 产物命名 + 版本递增 |
| 2 | `extras` 白名单漏 `repair-edge-missing` | QA 边界探针 | 合法 YAML 被误判为未知键 | 白名单补全 + 契约用例 |
| 3 | CLI 未装配回边栈 | QA 端到端 | `run_action extend-repair` 100% 失败 | 抽出 `build_orchestrator` 与 API 同构装配 |
| 4 | 终局卡片驳回空转 | 工程师实现自检 | 卡片 `stage_id == coding` 时 evaluation 未被作废，驳回后直冲终点 | `_apply_reject` 无条件作废下游 + 回退 `current_stage_id` |
| 5 | batch 终局补扫重复审计 | 工程师实现自检 | 审批记录多 1 条 | `_record_auto_approval` 幂等 |
| 6 | 前端修复轮 trigger 被清空 | 工程师实现自检 | 重放帧丢失「触发原因」 | 条件赋值 + 断言 |
| 7 | 沙箱镜像缺 `ruff`，预检误报 | **首次真跑基准** | 预检直接失败且提示误导 | Dockerfile 补 `ruff>=0.6,<0.7`；预检区分「缺工具 / docker 错误」 |

### 6.1 变异测试抓出的「测试有效性」缺口（非源码缺陷）

| 缺口 | 变异 | 补齐后 |
|---|---|---|
| 修复注入的「上一版不得在上游段重复」无用例 | 关掉去重 → 29 例全绿 | 双情形用例 + 空段消隐断言 |
| accept-best 未判别 total vs round | 改取 round 最大 → 原用例仍绿 | 逆序历史用例（71→62 接受 v1） |
| CLI 动作未断言调用 `_wake` | 删 `_wake` → 全绿 | `spawned == [run_id]` 断言 |
| store 同 round 去重无覆盖 | 去重失效 → 28 例全绿 | 双断言（轮次不增 + 字段覆盖） |
| judge 成本归属只断言对象属性 | 删传参 → 9 例全绿 | 断言 `gateway.chat` kwargs |

## 7. 已知限制（不阻塞 v1.1）

1. **CLI 是离线控制面**：`run_action.py` 动作落库并置 `running`，推进需 API 服务启动时 recovery 接管；服务在运行时请走 API。已写入 `docs/04 §9.2`。
2. **基线为部分执行**：`limit=3`，首轮/最终通过率只对这 3 个任务成立；全量 12 任务基线需再跑一次（预算约 ¥3–4）。
3. **`eval_verdict` 产物内部文件名仍为 `evaluation_report.json`**：产物名与内部文件名解耦（历史兼容），API 两种命名都能读。
4. **已知 flaky 观察项**：`test_in_flight_budget_error_during_repair_still_pauses` 曾 1 次失败（无 traceback 留存），此后单跑 10 次 + 全量 7 次未复现；复发时需保存 traceback，排查 paused/failed 状态竞态。
5. **单租户**：全实体预留 `tenant_id`，但 v1.1 未做 RBAC。

## 9. 遗留与 v1.2 建议

1. 跑满 12 任务基线（`--resume` 续跑，预算 ¥3–4），并在 README 更新全量首轮/最终通过率；
2. 开 judge 跑一次，对比 `--no-judge` 的评分差异与成本；
3. CLI 增加 `--api` 客户端模式（HTTP 直连服务），消除「离线动作需重启」的认知负担；
4. 为 flaky 用例引入确定性同步点（事件栅栏），或保留现场抓 traceback；
5. 跨版本事件重放：老帧缺字段时统一「条件赋值 + 契约用例」。
