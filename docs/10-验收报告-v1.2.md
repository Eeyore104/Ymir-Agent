## 1. 结论

**v1.2 核心目标达成**：从「从零生成一个能跑的项目」升级为「按用户既有工程的规矩把改动增量合进去，并安全推到自己的仓库」。三条主线——垂直模板库、增量 patch、GitHub 推送——全部实现，并在真实模型 + 真实沙箱下验证。

| 目标 | 结论 | 关键证据 |
|---|---|---|
| 垂直模板库 | ✅ | `fastapi-vue3` / `python-cli` 两套 YAML；`reserved`/`seed` 双类骨架真跑注入正确（`skeleton_added` 恰 3 项，seed 类由模型自生成不计入） |
| 增量 patch | ✅ | `mode=patch`、`base_content_hash=b35799d5…`、`noop_dropped=0`、`skipped_existing=5` 语义全部正确；产物只含增量 + 簿记文件 |
| GitHub 推送 | ✅ | Git Data API 九步走通；**`base_tree` 传 tree sha 未出现 422**；`.env` 被 `path_blacklist` 拦、`.env.example` 已推；分支保护生效 |
| 评测接入模板 | ✅ | 沙箱内**真实执行**模板 `checks` —— v1.2 首次让 `pytest` 在沙箱里真正跑起来（20 passed） |
| 真跑基线 | ✅ | 12/12 全量：首轮 **58.3%** → 最终 **83.3%**，自愈回环净增益 **+25pp** |

### 必须如实说明的一点

T5.1 的四场景中，**①-1 达 `conditional`，①-2 / ② / ③ 为 `fail`**，没有一个达到 `pass`。

但这三个非通过项的失败原因**全部是模型生成的代码有缺陷**——
缩进错误（`conftest.py:18`）、argparse 错误路径未处理、重写 `tests/conftest.py` 破坏回归基线——**不是 v1.2 的机制问题**。

机制本身在场景 ② 的产物里被逐字段验证正确：`mode=patch` / `base_content_hash` 非空 / `noop_dropped=0` / `skipped_existing=5` / 只有增量文件 + 簿记文件。

按 `docs/09 §9-T5.1` 的 DoD 原文，① 允许「双门槛通过**或失败原因明确（不允许 `unknown`）**」，三个场景均属后者，失败原因精确到文件与行号。

## 7. 过程中发现并修复的真实缺陷

T5.1 真跑暴露的 5 个缺陷（**全部是单元测试测不到的**）：

| # | 缺陷 | 性质 | 后果 | 提交 |
|---|---|---|---|---|
| **D1** | `truncate_pipeline` 只重建 `stage_completed` 主链 → 丢弃 `evaluation --evaluation_failed--> coding` 回边，且漏传 `repair` 配置 | **v1.1 能力盲区** | v1.1 最核心的「自愈回环」在**所有**单跑验证中都是死的（7 次 run 的 evaluation fail 全部直接 completed） | `9cb3f0f` |
| **D2** | `max_tokens` 被**角色级配置**覆盖（`gateway.py:204` 角色值优先），只改 `models.yaml` 无效 | 配置分层 | PRD / 架构 / 代码三阶段全部截断在 8192，`finish=length`；工程师范畴的 CodeBundle JSON 断在中间 | `7366207` |
| **D3** | `from_scratch` 也写 `patch_manifest.json`（无条件写入） | 契约违反 | 违反 DoD ⑨；让评测把全量文件当「变更文件」做 judge 语料分级 | `7366207` |
| **D4** | `CodeBundle` 无任何校验器 | 设计缺口 | 模型写错缩进也能过校验，要等沙箱 `pytest` 才炸（白烧整轮 ¥0.3 / 2 分钟） | `9cb3f0f` |
| **D5** | 沙箱镜像缺 `pytest-asyncio` / `greenlet` | 环境 | conftest `import pytest_asyncio` → exit 4；`sqlalchemy.ext.asyncio` → exit 1 | `629ad17` / `82f81af` |

> 这五条的共同点：**单元测试的替身（mock LLM、fake 沙箱、截断流水线）把真实故障路径全绕过去了**。
> 724 条测试全绿，不代表系统真能跑起来。

另有一条软约束（`9bb1e1b`）：增量提示词补「既有测试必须继续通过 / 勿重构测试基础设施 / 改动面最小化」。
**实测无效** —— 加约束后重跑场景 ③，模型仍重写了 `conftest.py`。

## 8. 已知限制（不阻塞 v1.2）

| # | 限制 | 影响 | 处置 |
|---|---|---|---|
| L1 | **模型增量质量不稳定** | 会重构测试基础设施与无关模块，导致既有测试全挂（场景 ②③ 的共同根因） | 提示词无效 → v1.3 需服务端硬约束 |
| L2 | **前端不做构建校验** | `fastapi-vue3` 模板前端只做结构静态检查，报告标「静态检查（未构建）」 | 设计选择（镜像无 node、离线无 npm registry），v1.3 候选 |
| L3 | **CI 不跑 `docker build`** | 镜像类问题（D5）永远只能人工验证 | 团队约定（构建需外网且耗时 15+ 分钟） |
| L4 | **单跑脚本无法产出四维分数** | `verdict` 是 QA 角色 LLM 判定，四维分数属 `run_benchmark.py` 路径 | 已在 `docs/09 §15.1` 写明口径 |
| L5 | **两种评分口径结论可相反** | judge 与确定性判定差异最大 28.3 / −26.7 分 | 正式口径定为确定性版；judge 作对照 |

## 10. 遗留与 v1.3 建议

详见 `docs/11-增量设计与任务列表-v1.3.md`。三条主线：

1. **增量质量硬约束**（对应 L1）—— 服务端保护基线测试文件 + 评测先独立跑基线测试套件
2. **前端构建校验**（对应 L2）—— 镜像加 node + 离线 registry 或跳过构建的显式口径
3. **模板库扩充**—— 从 2 套到 N 套，覆盖更多垂直场景

**v1.2 定稿判断**：实现 20/20 交付、724 测试全绿、CI 全绿、四场景 + 双口径基线齐备。
T5.1 三个场景非 `pass` 属于模型能力边界，已在 §1 与 §8 如实记录，**不影响 v1.2 作为工程交付的完整性**。
