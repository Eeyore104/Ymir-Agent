**② 的 DoD ④ 达成，证据链完整**：基线 4/4 检查 exit 0（pytest 34 passed）→ 合并树 `5 collection errors` → `regression=True` → `classify_failure` 落到 `"regression"`（不是 `check_failed`）。失败原因是 `ImportError: cannot import name 'run' from 'ymir_cli.cli'`——模型重写了既有入口、删掉了 `run`。

**① 的失败换了个原因，且更值得记**：`baseline_runnability.status=unhealthy`，挂在 **`fe-build` 的 exit=2** 上（`fe-build: 缺少 web/package.json`），不是 ruff。因为 **v2 是 patch 产物、只含增量**，`web/` 整个目录不在里面；而 `fe-build` 是 `blocking: true` ⇒ `blocking_failed=['fe-build web']` ⇒ `passed=False`。

QA 另做了**消融实验**证明这条与 ruff 严格度无关：同一棵 ① 合并树上，`ruff check .` 与 `ruff check --ignore B008 .` 的输出**逐行一致**（7 errors、exit=1、`diff` 为空）——因为 v2 缺 `ruff.toml`，骨架补缺注入的已是修好的那份，命令行再加 `--ignore` 属冗余。

另有一层：① 的 manifest 是 `added=0 / modified=3 / skeleton_added=3 / skipped_existing=2 / change_ratio=0.26`（分母 23）。**模型没有新增任何文件**——因为 `8ca19ae0 v2` 本身就是 v1.2 scene2 对**同一条需求**（加 priority）的产物（`app/models.py:15` 已有 `priority: Mapped[str]`），再提一次属需求撞车。

**顺带完成了「骨架补缺」的首次真跑验证**：`skeleton_added = [.env.example, pyproject.toml, ruff.toml]`（3 个，v1.2 全期为 0），`skipped_existing` 从 5 降到 2。这条分支此前**从未被真实数据触发过**（v1 是完整树，5 个骨架全部 skipped），本次证明它与优先级表逐条吻合，且注入的 `ruff.toml` 确为修好的那份（B008 在该合并树里消失）。

| 口径 | 结论 | 首个失败命令与原因 |

> **根因必须写准**：`baseline_probe` 把基线文件**原样**塞进沙箱跑 `checks`，不 merge、不注入骨架。
> 而 `fe-build` 是 v1.3 才新增的检查、严格 `ruff.toml` 也是骨架注入的——**v1.2 时代的产物从没被要求「前端能 build」，也不带严格 lint 配置**。
> 所以「任何 v1.2 时代的既有产物，用 v1.3 的 checks 去探都会 unhealthy」是**必然**结果，属口径升级而非代码退化。
> 这也说明 B008 修复**不可能**让旧产物达标——它只消除了「合规 FastAPI 写法恒被 B008 判违规」这一条**假阳性**。

> **「完整且严格口径健康的 fastapi 基线」在本版本中不存在。** v1 完整但过不了 SIM108，v2 健康但不完整（缺 `web/`、缺 `ruff.toml`）。
> ① 的 DoD ④ 无论换哪个都补不上；唯一出路是用 v1.3 模板**从零跑一次**生成新基线（需 API 额度，且不保证模型产出能过 lint）。
> **我不为"让 DoD 好看"花这笔钱**，也**不**去放宽 checks 让旧基线变绿——那会把 F7「归因冤枉模型」的问题反向扩大成「尺子放水」。
> 根因是 L7（没有 merged→baseline 落库动作），不是基线挑得不好。

#### DoD ④ 的最终判定（不粉饰）

| 场景 | DoD ④ | 原因 |
|---|---|---|
| ② `python-cli` | ✅ **达成** | 基线健康 + 合并树回归 + 归因 `regression`，三层证据齐 |
| ① `fastapi-vue3` | ❌ **不可达** | 两个叠加原因：①**增量产物不能当基线**（L7），v2 缺 `web/` → `fe-build` 阻断；②**需求撞车**（v2 已是同一需求的产物）→ 模型不新增文件（`added=0`） |

**结论：T1.2 的归因机制在 ② 上被真实数据证明成立；① 的缺口不是机制缺陷，是 L7 + L9。** 我不用"手工合成基线"去掩盖它——那样做会让 L7 这个 v1.2 遗留未交付项继续隐身。

#### DoD ④ 的三句话表述（不用一句"未达成"糊过去）

1. **② 达成**：v2 基线 4/4 check exit 0 + 合并树 5 个收集错误 ⇒ `regression=True`，`classify_failure` 真实输出 `failure_class="regression"`。**T1.2 的归因能力在"干净基线"上被证明。**
2. **① 不达成，根因有两层**：表层是 `fe-build` 阻断（增量产物不完整）+ 需求撞车（v2 已实现 priority ⇒ `added=0`）；**根因层是 L9** —— 旧产物 × 新 checks 的结构性错配。
3. **本版本不存在可验证的补救路径**：v1+旧命令 unhealthy（B008×4+SIM108）、v1+新命令仍 unhealthy（SIM108）、v2 unhealthy（fe-build）。想要"完整且严格口径健康"的基线只能**新跑一次 `from_scratch`**，且成败取决于模型当次产出质量。**我不为补齐 DoD 花这笔钱**，写成 L9 + v1.3.1 项更诚实。

#### 受保护路径：4 次真跑仍未触发

所有 run 的 `protected_hits = 0`、`conflicts = []`、无 `protected_retry` 键、`merged.files["tests/conftest.py"]` = 基线原版。T1.1 三段式**只有单测证据**（38 例全绿），真跑从未触发——这一点必须如实写，不能拿"机制已实现"代替"已被真实验证"。

#### T1.3 改动面告警：真跑生效

第一轮两场景 `change_ratio` = **0.56 / 0.53**，各记 1 条 `change_ratio_exceeded` 短码，未阻断。两个 manifest 都**无 `protected_hits` 键**（=0，走「非默认值才序列化」），`base_content_hash` 与基线版本行指纹逐字节相等。

#### 一个必须说清的口径

`scripts/run_single_role.py` **不注入 `eval_gate` / `repair`**，所以单跑永不产生 `EvalVerdict`、永不进自愈回边。T5.1 里的「verdict」是 **QA 角色的 `pass/conditional/fail`**（`roles/schemas.py:158`），不是 `EvalVerdict`。
`failure_class` 由 QA 额外调 `HarnessEvaluationGate` 取得——gate 与 benchmark **两层分工**：gate 的 `failure_class` 只写 `check_failed|budget_exceeded|...`，`regression` 由 `benchmark.classify_failure` 依据 gate 携带的 `regression` 布尔映射得出。**所以"gate 没写 regression"不是缺陷，是设计。**

**T5.1 累计成本**：第一轮 ¥0.9524 + 第二轮 ¥0.5673（两次 run + 探针 + gate 复核）= **¥1.5197**。所有证据归档在 `data/v13/`（含 `INDEX.md`、每 run 的原始日志、`TaskOut` 全量 JSON、manifest 原件、合并树回放脚本与输出）。

## 2.1 T5.3 兼容性契约回归（QA 独立执行，只跑不改）

## 4. 沙箱镜像（v1.3 最大环境变更）

| 指标 | v1.2 基线 | v1.3 实测 | 判定 |
|---|---|---|---|
| 镜像体积 | 326 MB | **968 MB**（+642 MB） | < 1.6 GB 拆分线 ⇒ 不拆 |
| `docker build` 耗时 | 未记录 | **≈ 224 s**（3.7 min） | < 8 min ⇒ 不拆 |
| 断网 `fe-build`（有 lock） | 不可用 | **4 s**（`npm ci --offline` 命中 `/opt/npm-cache`） | ✅ |
| 断网 `fe-build`（无 lock） | 不可用 | **48 s**（回退 `/opt/fe-baseline`，含 ~150 MB 复制） | ✅ |
| 断网 `node-build` | 不可用 | **5 s**（回退 `/opt/node-baseline` + `tsc`） | ✅ |

**镜像内工具链（断网实测）**：node 20.20.2 / npm 10.8.2 / Python 3.12.15 / pytest 8.4.2 / ruff 0.6.9 / pandas 2.3.3 / numpy 2.5.4。

体积构成：`/opt/fe-baseline` 154 MB、`/opt/node-baseline` 31 MB、`/opt/npm-cache` 29 MB、node 运行时 ≈117 MB、pandas/numpy 所在 pip 层 272 MB。

> **如实说明**：原 DoD 要求体积增幅 ≤ 250 MB，实测 +642 MB，**超 2.5 倍**。
> 原因是"断网可构建"必须把 node 运行时 + 依赖池 + npm 缓存都塞进镜像；砍掉 `npm-cache`（29 MB）能让体积略降，
> 但会让 4 s 的主路径失效、退化为 48 s 的复制路径。**用体积换断网可构建性**，这是有意取舍。

### 独立验证：v1.2 基线产物能否在新镜像构建

主理人用 v1.2 场景②的基线产物（27 文件，vue 3.4 + element-plus 2.7 + vite 5.2）在 `--network none` 下跑 `fe-build web`：

```
dist/index.html                     0.39 kB │ gzip:   0.29 kB
dist/assets/index-Cailtaz3.css    361.62 kB │ gzip:  48.31 kB
dist/assets/index-5Yv_eZqh.js   1,028.43 kB │ gzip: 336.83 kB
✓ built in 15.56s
```

这条验证有两重意义：①依赖池确实覆盖 `@vitejs/plugin-vue`；②T1.2 的基线探测会走"基线健康"路径，不会因基线自身失败而降级 `unknown`。

### 6.4 T5.1 真跑暴露的模板缺陷

| # | 缺陷 | 性质 | 处置 |
|---|---|---|---|
| **T1** | `fastapi-vue3` 的 `ruff.toml` 规则集 `select` 含 `B` 但**无 ignore**，而 `B008` 与 FastAPI 官方写法 `db: Session = Depends(get_db)` 天然冲突 ⇒ 该模板下任何**合规**代码恒吃 ≥1 条 B008 | 模板配置缺陷（不是模型问题） | **已修，分两层**：①骨架 `ignore = ["B008"]`（管 `from_scratch` 与缺配置的基线）；②检查命令 `ruff check --ignore B008 .`（管「基线自带旧配置」）。实测：旧命令 4 errors → 新 2 errors（只 B008 消失、`F401` 仍报）；镜像内 E2E 旧命令 exit=1 → 新命令 exit=0。并补断言锁死「其余三套模板不得含 B008」 |

> **为什么必须分两层（这条是本次最容易做错的地方）**：`merge_trees` 的骨架优先级是「**基线已有该路径 ⇒ 骨架完全不参与**」（记 `skipped_existing`）。
> 只改骨架 ⇒ 对 v1 那种自带旧 `ruff.toml` 的基线**完全无效**；只有命令层 `--ignore` 才能覆盖它（ruff 0.6.9 的 `--ignore` 是**追加**语义，不会顶掉配置里已有的 ignore，且该版本无 `--extend-ignore`）。
> 这属于「改在了错误的层级」——与 F1 那个「内存改了、落盘没改」是同一类失效模式。

> **真实合并树验证（27 文件基线 ⊕ ①c 补丁，零模型成本）**：
> 合并树 `ruff.toml` 与基线**逐字节相同**（`skipped_existing` 含 `ruff.toml`、`skeleton_added=[]`、模板骨架里虽有 `ignore B008` 但没被用上）——
> 直接证明"改骨架救不了已有基线"。
>
> | 命令 | exit | B008 | 其他 |
> |---|---|---|---|
> | `ruff check .`（旧） | 1 | **6** | F401×2、UP035×1 |
> | `ruff check --ignore B008 .`（新） | 1 | **0** | F401×2、UP035×1 |
>
> 且 `SIM108` / `UP017` / `F401` / `I001` 在新命令下**仍全部被选中**（`select` 未被削弱）。
> **新命令 exit 仍为 1** —— 因为该补丁本身确有未使用导入与过时 API。这条最能说明性质：**豁免去掉的是框架冲突噪音，不是真缺陷。**
| **T2** | **保护面窄于破坏面**：② 里模型没碰 `conftest.py`，而是重写既有业务入口 `ymir_cli/cli.py` 删掉全部既有子命令 → 24 个既有用例失败 | 设计边界 | 登记 v1.3.1：把「既有入口文件」纳入 `protected.paths`，或引入「改动基线既有文件需显式豁免」的默认策略 |
| **T3** | `fe-build` 只在**评测**阶段跑，`smoke_report.json` 里只有模型自测的 pytest ⇒ QA 角色证据链看不到构建结果（本轮因此写了一条"前端构建结果缺失"的误判风险） | 证据链缺口 | 登记 v1.3.1：把 `group=frontend_build` 的命令同步进 engineer 阶段冒烟 |
| T4 | 模型自己产出 `code.json` 索引文件，被计入 `changed_paths`，轻微抬高 `change_ratio` | 观察项 | v1.2 基线也有此文件，非回归 |

另有两处**口径事实**（不是缺陷，但必须写清）：
- `run_single_role.py` **不注入 `eval_gate` / `repair`** ⇒ 单跑永不产生 `EvalVerdict`、永不进自愈回边；单跑的「verdict」是 QA 角色判定
- `--evaluate` 会额外产生 3 次 judge 调用，但 `print_report` 的「合计」只统计阶段调用 ⇒ **单跑成本会低报**；本报告成本取自 DB `model_calls` 全量

### 6.5 第二轮真跑新发现的三条 P2（均不阻塞定稿）

| # | 问题 | 性质 | 建议 |

## 7. 已知限制（不阻塞 v1.3）

| # | 限制 | 影响 | 处置 |
|---|---|---|---|
| L1 | **保护面窄于实际破坏面**（T5.1 真跑实证） | ② 里模型没碰 `conftest.py`，而是重写既有业务入口 `ymir_cli/cli.py` 删掉全部既有子命令 → 24 个既有用例失败。`protected.paths` 挡不住；T1.2 本应判 `regression` 兜底，却又被 unhealthy 基线短路 | v1.3.1 扩保护面（既有入口文件）或改「改既有文件需显式豁免」策略 |
| L2 | **前端构建依赖镜像预置依赖池** | 模型若在 `package.json` 里引入池外依赖，断网构建必然失败（`npm ci --offline` 与回退路径都装不上） | 这是断网沙箱的固有边界；靠 `fe-build` 的可读错误摘要暴露 |

| L5 | **v1.3 基线分数不可与 v1.2 横比** | 分组配分 + `allowed_prefixes` 修正同时生效 | 见 §5 口径断点，已在 `docs/04 §12` 写明 |
| L6 | **`MANIFEST_MAX_BYTES` 仍无强制点** | 仅测试断言，运行时无截断 | v1.2 既有状况；强截断会破坏 `changed_paths` 作为 judge 语料输入 |
| **L7** | **增量产物不能作为下一轮增量的基线**（**v1.2 遗留的未交付项**，不是 v1.3 引入的退化） | `docs/09 §4.3` 的 R9④ 原文承诺「提供『以合入结果为新基线』显式动作」，**设计上承诺过、实施时漏了**：`src/ymir/` 里只有 `POST /projects/{id}/baselines`（上传用户快照），没有任何 merged→baseline 落库路径；而 patch 产物只存增量 + 簿记（`docs/09 §4.2.2` 设计使然）。后果：用户想连续做两次增量，只能回到 from_scratch 的全量产物；`fe-build` 这类需要完整目录的检查会直接不可用（F8） | v1.3.1 P2：补 R9④ 的「合并树另存为新基线」动作 |
| **L8** | **增量模式下 QA 的 verdict 系统性失真**（F9） | QA 只看得到增量产物、看不到基线文件，会把「基线里本来就有的文件」判成缺失；① 的 `fail` 有一部分基于此误判 | v1.3.1：把基线条目清单与回归结论注入 QA 上下文 |
| **L9** | **T1.2 对存量产物结构性失效**（能力边界，比"基线选得差"更本质） | `baseline_runnability` 用**当前模板的 checks** 度量基线产物，而基线可能是旧模板产物。三类错配：①旧产物缺当前 checks 依赖的文件（v2 增量产物无 `web/package.json` ⇒ `fe-build` exit=2）；②当前 checks 引入了旧产物生成时不存在的要求（`fe-build` 是 v1.3 新增）；③同一棵树两把尺子（v2 原样 ruff 0 errors vs 合并树 7 errors）。**后果**：`baseline_status=unhealthy` ⇒ gate `unknown(baseline_unhealthy)` ⇒ `regression` 永远不触发 ⇒ **T1.2 对"存量用户"实际上不可用，只在"v1.3 新生成的基线"上有效** | v1.3.1：probe 记录/比对模板版本；「基线从未提供该 check 依赖的文件」记 `skipped` 而非 `failed`；或按模板版本选 checks 集 |

> **L7 的直接后果（本轮验收被它卡住）**：这个版本里**根本不存在一个"完整且严格口径健康"的 fastapi 基线** ——
> v1 是完整树但过不了模板 lint（B008×4 + SIM108），v2 是健康但缺 `pyproject.toml` / `ruff.toml` / `.env.example`
> （它是 patch 产物，只含增量）。所以 T5.1 DoD ④ 在 fastapi 场景的缺口，根因不是"挑错了基线"，而是这个结构性缺口。

1. **增量质量继续硬化**：把"改动面告警"升级为"超阈值要求人工确认"（HITL 门）
