### 必须如实标注的八条边界

> 不写这八条，"全部达成"就是过度声称。

1. **A6 是 PARTIAL，不是 PASS**（用户 2026-11-02 批准接受）。原因见 §6.1：`code.json` 在**编码阶段**就已落盘，而归因标记在**评测阶段**才产生，接线要动"评测回写产物"的结构，属 v1.5。
2. **R-c 是 PARTIAL**：场景（"给已有 stats 模块加子命令"）与基线重叠，模型必然重写同名模块、删掉 `StatsResult`；真跑证明 ★2 的"保留编辑 + 按基线插回符号"**按设计工作**，但树仍不可运行（`data/v14/§5`）。
3. **模板的 `blocking` 集合只有 `fe-build web`**：后端 `pytest` 失败**不**进 `blocking_failed` ⇒ "后端导入即炸、前端能构建"的树会被判 `healthy`。这是判据覆盖范围，不是闸门失效；**未**为了让 R-b 好看去改配置。
4. **`unhealthy` 分支的真跑证据是受控样本**：v1.3.1 的历史坏树因 `template_hash` 变更（`7dfd0853…` → `b652733e…`）无法重建，只能构造。已在 `data/v14/§4.4` 明确标注"非真跑结论"。
5. **CLI 入口不装配 repair stack** ⇒ CLI run 永不落 `eval_verdict`，`from-merge` 只能走 fail-closed。属既有架构事实（非本版引入）。
6. **`POST /projects/{id}/evaluations` 不绑定模板 checks**（只取 `suite.tasks[0].checks`）⇒ 该路径算不出 `blocking_failed`。本版只修好它的"版本自证"（Q-R4-02），未改它的 checks 口径。
7. **`revert` 只保证 `def`/`class` 依赖闭合**（单文件上限 64），模块级**赋值**与 `import` 别名不还原 ⇒ 不保证整棵树可运行。这是能力边界，已在 `docs/04` §11.4 写明。
8. **闸门读的是"已有报告的结论"，不重跑探针**（零额外沙箱调用是设计目标）。因此：① 报告正文可被人工改写 —— 本地产物本来就可改，这条判据是"防串味"不是"防伪造"；② 报告路径下 `skipped` 一律按未知（只有探针路径才把"跑不了"当放行），因为报告里"全跳过"没有一条跑过的证据；③ 报告绑 `(run_id, artifact_version, artifact_name)` 三元组，任一缺失即 fail-closed。

### 3.1 R-a（★2）：真跑命中，PASS

### 3.2 R-b（★3）：PASS，但 `unhealthy` 用受控样本

- **真实**：run `29f52b8f` 无 `eval_verdict`（CLI 不装 repair stack）⇒ `from-merge` 返回 **409 `baseline_health_unknown`**；带 `force=true` ⇒ **201** + `warning=baseline_promoted_unknown:1`。

### 4.2 一条环境纪律：本机不能用退出码判 pytest

本机存在 safe-delete hook（拦截 `shutil.rmtree` 一类调用），会让 pytest 在**零失败**时也返回
`exit=1`。本版所有"绿/红"判定一律以 `--junit-xml` 的 `failures/errors` 为准；变异验证同样如此。
另有一条更隐蔽的坑：用系统 `python`（3.13 沙箱解释器）跑 `-m pytest` 会因缺依赖直接失败，
看起来像"变异被杀"，其实是解释器错了 —— 变异脚本必须显式用 `.venv/Scripts/python.exe`。

## 6. 已知限制（不阻塞验收）

### 6.1 A6 为什么是 PARTIAL（不是没做，是位置不对）

`sample_markers` 是**评测阶段**的产物（`failure_attribution.sample_markers`），而 `code.json` 在
**编码阶段**就已落盘。当前实现做到了"写入口支持 + 空值不写键"（`code_writer.build_code_files`），
但**没有生产调用方**把评测期标记回写进 code.json —— 那需要"评测回写产物/新开一版 code"，会改动
产物不可变契约。过滤那一半（T4.1）已完整落地并有单测。

### 6.2 判据覆盖：`blocking` 只有 `fe-build web`

模板 `blocking` 集合只含前端构建，因此"后端 `pytest` 全红、前端能构建"的树会被判 `healthy`
（R-b 第 1/3 号 run 实测）。这是**判据的定义**，不是 bug；扩容属配置/产品决策，v1.4 未动。

### 6.3 闸门只对"有报告的 run"生效

`HarnessEvaluationGate` 只在 API 全链路（`mode=batch`）装配；CLI 单跑不落 `eval_verdict`。
所以 CLI run 的提升请求只能走 fail-closed（`force` 人工通道）。这是架构现状。

> 返修 5 之后，**Web 用户的补评测已能解锁**（服务端按产物版本行反查 `run_id`），
> 但前提是该版本确实由某个 run 产出（`artifact_versions.run_id` 非空）。若版本来自
> 手工导入/脚本写入（没有归属 run），反查返回 `None`，仍按未知 fail-closed —— 这是
> **有意为之**：没有归属就没有"哪次运行的结论"可言，不能编造。

### 6.4 `revert` 的能力边界

只闭合 `def`/`async def`/`class` 依赖（单文件上限 64）；模块级赋值、import 别名不还原。
R-c 证明：闭合之后仍可能因为"模型换了数据模型"而不可运行 —— `revert` 保证"符号不丢"，
不保证"语义仍自洽"。

### 6.5 `POST /evaluations` 的 judge 成本仍不归属任何 run

返修 5 反查出的 `run_id` 只补进**报告根部**与**报告产物版本行**，用于闸门取报告；
**没有**传给 `EvalTask`，因此该端点的 LLM judge 成本在 `model_calls.run_id` 里仍是 `NULL`
（QA R6 `Q-R6-01` 实测）。原因是 `EvalTask.run_id` 还参与 `harness._baseline_ref_of` 的基线解析，
改它会顺带改变"补评测拿哪棵树当基线"的口径 —— 属 v1.5 的语义决策，不在本版返修范围内。
按 run 统计成本时，`data/v14/INDEX.md` §2 的"未归属调用"就是这部分。

## 7. 遗留与后续建议

### 7.1 进 v1.5（按优先级）

1. **`unhealthy` 的真跑证据**：用当前模板重新造一棵坏树（`blocking` 命中 `fe-build`），把受控样本替换成真跑。
2. **`blocking` 判据扩容**：后端 `pytest` / `import` 进 `blocking_failed`（需先解决"镜像里没有项目依赖"的误报）。
3. **`POST /evaluations` 绑定模板 checks**：与 run 内 gate 同口径，否则"补评测"给出的报告天然弱于 gate 报告。
4. **A6 收口**：评测期标记回写产物（新开 code 版本或写独立 `attribution.json`），让 `code.json` 真正带上标记。
5. **`revert` 的赋值依赖**：`CONST`/工厂实例的还原（当前只还原 def/class）。
6. **CLI 装配 repair stack**：让 CLI run 也落 `eval_verdict`，否则 CLI 路径永远 fail-closed。
7. **评测对话框显示归属 run**：返修 5 改成服务端按版本行反查，用户无需选；但界面上看不到"这次评测算在哪个 run 头上"，排查时只能查库。v1.5 可在对话框只读展示 + 允许覆盖。
8. **补评测的 judge 成本归属**：把 `run_id` 传进 `EvalTask`（让 `model_calls.run_id` 有值），
   同时明确它对 `harness._baseline_ref_of` 的影响（§6.5）—— 属语义决策，需先定"补评测用哪棵树当基线"。

### 7.2 本版**未**做的事（避免后人误读）

- 未改任何模板的 `blocking` / `protected` 语义（除 T5 的 B008 写法）；
- 未引入新的模型能力或提示词策略（`revert` 是纯函数兜底，零模型调用）；
- 未改产物不可变/版本契约（A4 特意不写 `patch_manifest.json`）；
- 未做多租户/RBAC 的任何扩展。
